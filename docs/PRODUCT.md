# 原点工作台 · 产品需求文档

版本：0.1.0 源码预览版。产品设计与维护：王子瑜 ZiYu。

本文描述原点自己的产品目标、交互与业务约束。功能是否通过验证，以 [验证记录](VALIDATION.md) 为准；需求条目不等于所有平台都已支持。

## 1. 从什么问题开始

一个人创作产品时，真正费力的通常是：想法散落在聊天和笔记里，资料与结论失去联系，同一段背景反复填写，方案修改后旧文档仍在流传，最后交付的人还要重新追问关键条件。

从第一性原理看，产品创作至少需要保留五件事：原始输入、可检查的依据、明确的取舍、可实现的描述、真实的验证结果。工具的作用是减少这些对象之间的搬运与遗失，让人把精力用于判断。

原点的核心任务：**让个人从一个尚未想清楚的念头，逐步形成有依据、有边界、有验收条件、可以交接的产品方案。**

## 2. 服务谁，以及怎样判断有用

主要用户是自己推进产品的人：个人产品经理、独立开发者、设计师，以及需要把业务想法解释清楚的人。允许用户不了解 PRD、用户故事或优先级模型，界面先说清当前要解决的问题。

典型场景：

1. 灵感刚出现，先记录，不被一整套问卷打断。
2. 拿到访谈、截图、竞品资料，把原文与自己的理解放在同一个项目。
3. 对多个方案做取舍，记录选了什么、放弃什么以及为什么。
4. 将方案交给开发者或编程工具，能说清首版范围、验收与未决问题。
5. 做完实验或试用后，发现旧判断不成立，回看并调整。

衡量有用的指标是重复填写是否减少、关键结论是否可追溯、交接后追问是否减少、修改是否可恢复。预览版尚未收集真实使用样本，不宣称已达到这些指标。

## 3. 产品原则

- 保留原话和原件，派生内容不能覆盖它们。
- 将事实、假设、模型建议、人工决定分别记录。
- 让用户逐步推进，允许不知道、跳过与稍后补充。
- 复用已填信息，尊重手动覆盖和有意清空。
- AI 可以提出意见；确认、取舍与定稿由用户完成。
- 更改重要输入时，提醒受影响的产物复核。
- 把失效、失败和未验证明确显示出来，不把空白包装成成功。
- 以普通文件交付，让产物可以独立阅读和继续制作。

## 4. 主要操作路径

```text
首页记下原话
  → 新建或归入项目
  → 产品蓝图：问题、使用者、场景、成功条件
  → 需求与验收：首版范围、稳定编号、正常与异常结果
  → 检查与交付：补具体缺口、整理新 PRD、导出
  → 验证与回看：写下实测结果、继续或调整
```

资料、方法、决策、偏好、画布和模型评审可在主路径需要时使用。无需先配置模型才能创建蓝图、需求和 PRD。

## 5. 功能与验收

### F01 想法收件箱

输入可以是不完整的一句话，先原样保存。未提交的草稿在本机暂存，可归入项目或搁置。

正常验收：写下原话，保存后再次打开能读到相同内容；尚未提交时切页或重开可继续。

对抗验收：保存请求尚未返回时继续输入第二条，第一条的返回结果不能清空第二条；服务失败时不能丢失输入或提示已经保存。

### F02 项目空间

项目包含标题、目标、阶段与相关创作对象。可创建、修改、归档和恢复。对象只能引用同一项目中允许关联的资产；项目偏好可覆盖同名全局偏好。

正常验收：在一个项目中创建的资料、决定和文档能在该项目找到；归档后可恢复。

对抗验收：错误项目 ID 或跨项目关联被拒绝；恢复包作为新项目导入，不覆盖原项目。

### F03 产品蓝图

蓝图逐步记录一句话想法、真实问题、使用者、场景、成功条件、限制、范围、非目标、流程、数据、风险、负责人和未决问题。

已完成的 PRD 方法答案可带入相应字段；手动保存的蓝图优先。用户有意清空字段时，不能把旧方法答案悄悄填回。缺失内容保留为待补充，不编造访谈结论或统计。

正常验收：已有方法答案进入蓝图及 PRD 正文，减少重复搬运。

对抗验收：保存途中继续修改，返回旧数据不能覆盖新输入；暂存与已保存内容分清；不完整蓝图仍可保存。

### F04 需求与验收

每项需求包含稳定编号、名称、描述、优先范围和两种验收：正常情况下应发生什么，失败或误操作时怎样处理。需求可属于第一版或稍后。

编号采用 `FR-001` 等形式，归档不复用编号，编辑不能改号。需求不是一串技术任务，先说明用户结果。

正常验收：首版需求进入 PRD；编号在编辑、历史、导出和恢复后仍可追踪。

对抗验收：导入重复编号、同一需求历史改号或非法字段时拒绝整项操作，不制造表面可用但内部冲突的数据。

### F05 资料与引用

支持 PDF、Word、演示文稿、表格、CSV、Markdown、文本、HTML 及常见图片。保留原件、哈希、解析结果与状态。文本 PDF 走轻量解析，扫描内容与图片在 macOS 使用本地 OCR。

引用绑定原文及其版本，查看时能定位到当时的内容；有页码时显示页码。部分解析与完全成功分开显示。

正常验收：文档正文、中文内容、页码与原件可对应；原件不被摘要替换。

对抗验收：损坏文件、超限文件、空白扫描页、无法识别的图片有明确结果；HTML／Markdown 中的远程与本地资源不由解析器主动读取。文件解析有数量、体积与超时上限。

### F06 产品方法

本地方法库提供原始方法说明与精选分步流程。方法实例保存当前进度、答案和采用的方法版本，可中途离开后继续。

正常验收：完成发现或 PRD 方法后，答案可以复用到蓝图和正文；原始方法内容与版本可查。

对抗验收：方法版本变化不能悄悄套用旧步骤；未回答完的步骤不能被标成完成。引入的方法原文继续保留许可与作者来源。

### F07 决策卡

决策至少说明问题、多个选项、选择、理由、依据和反证。候选意见可以保存为草稿，正式确认由用户明确操作。

正常验收：确认后留下版本与当时依据；修改来源会提示相关文档、画布待复核。

对抗验收：选项不足、选择不在选项中、缺少理由与依据时不能完成确认；模型输出不能绕过确认接口直接变为正式决定。

### F08 个人偏好档案

偏好有全局和项目范围，支持确认、停用与历史。项目同名偏好优先。记录偏好旨在减少反复解释，同时保留改变主意的空间。

正常验收：当前项目采用有效偏好，能回看版本和确认状态。

对抗验收：项目包带出的相关全局偏好在接收环境恢复为待确认的项目偏好，不静默改写接收方全局设置。

### F09 方案画布

提供真实可编辑的脑图与图形画布，支持文字导图、Markdown／Mermaid 插入预览、保存、草稿恢复、历史和导入导出。复杂视觉设计仍可使用外部设计工具。

正常验收：修改后的结构能再次编辑；插入先预览；历史版本可读。

对抗验收：损坏或不受支持的画布文件不能替换当前版本；保存失败不显示已保存，离开未保存内容有保护。

### F10 模型评审

用户自行配置模型服务，选择上下文后发起评审。支持最多四路并行、独立失败与重试，保留旧尝试。回答可以成为待确认草稿。

正常验收：正确组合流式片段，显示每路状态；一次失败不抹掉其他结果。

对抗验收：中断的响应保留已有文本并明确不完整；错误响应不当成答案；不通过评审结果直接修改确认过的决定。模拟协议测试通过不等于每一家真实服务的效果已验证。

### F11 检查与 PRD

检查展示具体缺口：关键蓝图字段、占位文字、首版需求、正常与对抗验收、未决问题、未确认决定、待复核产物等。可以点击回到需要补充的位置。

整理 PRD 时创建新草稿，记录使用的来源及其版本，不覆盖原有手写文档。可以比较前后稿，并查看当时采用的决定和证据。

正常验收：需求与方法答案进入正文；旧 PRD 与新 PRD 同时保留；历史来源可读。

对抗验收：结构齐全不能被表述为事实正确或商业可行；未确认判断必须显露其状态；输入改变后旧产物收到复核提醒。

### F12 交付、恢复与备份

交付 ZIP 围绕所选文档组织：PRD、采用的需求与验收、来源快照、相关原件、采用的画布文件、待核对事项和校验清单。包内链接使用相对路径，接收者不需要安装原点。

项目包用于恢复，包含更完整的项目对象、历史与原件。项目包不含模型密钥。应用打开时定期更新当日项目备份，保留最近七天，恢复为新项目。

正常验收：交付包可独立阅读；恢复项目能保留关系与历史；所有文件可依据清单校验。

对抗验收：未被文档采用的私人资料不随交付包带出；篡改、缺件、路径越界和超限包被拒绝；备份失败保留上一份有效备份。完整项目包不等于整机模型配置和全部全局偏好的备份。

## 6. 数据与状态规则

核心对象为项目、想法、资料、引用、方法实例、决定、偏好、画布、文档、需求与验证记录。对象具有 ID、类型、状态、版本、正文、关系和时间信息；具体契约在 `desktop/packages/desktop/src/common/types/studio.ts`。

- 编辑使用版本检查，冲突时保留当前输入并提示重新载入。
- 来源变化通过依赖关系提示下游产物待复核，不自动替用户改正文。
- 模型建议进入草稿，人工决定通过明确确认形成。
- 导入重新映射对象 ID，保留包内关系并验证引用完整性。
- 验证记录至少包含假设、方法、通过条件、实测结果与理由；没有实测结果时保持待验证。

## 7. 体验与运行约束

界面以中文与简洁桌面布局为主。主路径突出一步，补充工具按需展开；原文、版本、失败原因尽量用人能读懂的文字展示。

日常启动使用生产构建。资料解析按任务启动，画布按需加载；刷新在上一轮完成后再调度，隐藏窗口暂停周期请求，返回窗口时刷新。此设计避免请求叠加，不承诺任何资料规模下的内存上限。

个人项目默认存于本机。导出、调用模型及打开公开反馈页面均由用户明确触发。GitHub 源码仓库不包含私人资料、运行时、密钥或数据库。

## 8. 当前边界与后续顺序

预览版聚焦单人桌面创作。多人实时协作、移动端、在线账户同步、自动完成需求验证、无条件正确的 AI 决策、签名安装包不属于当前已交付能力。

后续按以下顺序验证：

1. 使用一个真实想法走完主流程，记录重复提问和交接追问。
2. 在另一台干净的 Apple Silicon Mac 完成安装、恢复和同一流程。
3. 验证复杂扫描资料、大型画布、长时间运行和批量解析。
4. 用真实模型配置评估质量、成本、延迟与恶意资料的影响。
5. 在证据充分后制作精简、签名、公证的安装包，再考虑跨平台。

每次功能测试后运行对应对抗案例：输入不完整、响应变慢、保存中继续编辑、来源已经变化、文件被篡改、没有真实验证结果。通过这些测试说明已覆盖的行为，不能替代真实用户验证。
